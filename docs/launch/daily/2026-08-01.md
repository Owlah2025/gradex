- [x] **2. Implement non-enumerating reset request and single-use consumption — 120 minutes.**
  Identical response for known, unknown, unverified, and suspended Accounts. Reset secrets are stored
  as digests, expire, bind to purpose, and are consumed exactly once under a row lock.
  **Stop condition:** real PostgreSQL race tests prove exactly one consumption winner, byte-identical
  request responses across all Account states, and refusal of expired, replayed, and
  wrong-purpose secrets. **Met — see below.**

  Migration `0007` widens the closed `identity_action_secrets` purpose allowlist to admit
  `PASSWORD_RESET` and the security-event allowlist to admit `PASSWORD_RESET_REQUESTED` and
  `PASSWORD_RESET_COMPLETED`. No new table: the digest-only storage, expiry, one-live-per-purpose
  index, terminal-state exclusivity, and attempt evidence recovery needs already exist.

  **Must 1 validated itself here.** `MaxSchemaVersion` moved to 7 and `migrate max-version` reported
  7 with no CI edit at all — the exact drift that failed S1B2's hosted CI.

  **The reset-completion route is deliberately absent.** `recoveryCommands` exposes only
  `RequestPasswordReset`. Consumption exists as unexported primitives — `lockResetSecret` and
  `consumeResetSecret` — that require a caller-held row lock, and the single-winner proof drives them
  in-package. Exporting a standalone consumption operation would create a supported way to burn a
  reset secret without replacing a password, stranding the Account. Must 3 consumes it in the same
  transaction as password replacement, revision advancement, all-family invalidation, evidence, and
  outbox intent.

  Eligibility follows the authoritative Account and password-credential lifecycle: `ACTIVE`, verified
  email, and an existing `password_credentials` row. Role is deliberately not in the predicate, so
  Instructors and Admins keep a self-service path. `CHANGE_REQUIRED` stays eligible, since that state
  means the holder must set a new password — exactly what recovery does.

  Non-enumeration is evidenced at the transport boundary, not at the service return value. Status,
  exact body bytes, `Content-Type`, `Cache-Control`, `Set-Cookie`, `Location`, and timing class are
  identical across unknown, unverified, active, and suspended Accounts, while exactly one live secret
  exists afterwards and it belongs to the active Account — so the equivalence hides a real difference
  rather than describing four identical no-ops.

  Every new test was mutation-checked. Dropping the purpose predicate, the expiry check, or the
  supersession check each failed its test; leaking ineligibility as an error broke the HTTP
  equivalence proof. The supersession case failed twice, once by test and once by a database
  constraint refusing a terminal secret.

  **A latent S1B1 defect surfaced and was fixed.** Supersession stamped `superseded_at` from a
  timestamp taken before the transaction began and before it waited on the Account row lock. Under
  concurrency, lock order and generation order invert, so an older `superseded_at` lands on a newer
  row and trips `identity_action_secrets_superseded_after_issue` — a 500 on an ordinary second
  request. It reproduced in 3 of 5 concurrent requests under `-race`. Both the new reset path and the
  **existing S1B1 verification resend path** carried it; `superseded_at` is now clamped with
  `GREATEST(issued_at, $1)` in both. The existing identity-package concurrency test could not catch
  it because it injects a frozen clock, making every `issued_at` equal. A new HTTP-level regression
  test runs on the real clock, and reverting the fix makes it fail in 3 of 3 runs.

  One security decision needed the developer: `recovery.go` was added to the `expose-guard.sh`
  allowlist for the reset bearer crossing into authenticated outbox encryption. Same boundary and
  reasoning as the already-approved `admission.go` entry; the digest, never the bearer, reaches
  `identity_action_secrets`.

  The four conditions attached to that allowlist approval were then verified directly. `recovery.go`
  contains no logging of any kind; every `fmt.Errorf` wraps a driver error with a static message and
  interpolates no token, bearer, or password; `insertActionSecret` persists `secret.Digest` only; and
  the file's two `Expose()` calls are the outbox bearer and the Argon2id hash bound for PostgreSQL,
  with no third site.

- [x] **3. Implement atomic password replacement with all-family invalidation — 120 minutes.**
  Replace the credential, revoke *every* session family, co-commit Identity security evidence and
  outbox notification intent in one transaction, and require a normal login afterward. Recovery
  issues no session.
  **Stop condition:** a recovered Account's every pre-existing family is denied, no session cookie is
  issued by recovery, and evidence plus outbox intent co-commit or roll back together. **Met.**

  `CompletePasswordReset` commits secret consumption, credential replacement, revocation of every
  family with reason `PASSWORD_RESET`, session-epoch advancement, Account revision advancement,
  `PASSWORD_RESET_COMPLETED` evidence, and notification intent in one transaction. The completion
  carries no Account identifier: the secret is the only thing that names an Account, so a valid
  secret cannot be aimed at a different one.

  Both revocation mechanisms are used, because they cover different windows. Revoking the rows kills
  families that exist now; advancing `session_epoch` invalidates every family admitted under the old
  epoch, closing the gap where a family created concurrently with the reset would otherwise survive.

  Recovery issues no session, proven by asserting the total family count is unchanged rather than
  only that none is active — so a mailbox compromise cannot be converted straight into an
  authenticated browser session.

  Ordering was chosen so a refusal costs the user nothing. Argon2id hashing and password screening
  run before the transaction opens, which keeps the Account row lock off the expensive path and makes
  an invalid secret cost the same work as a valid one. A weak password is refused with the reset
  secret still live, so the same link can be retried.

  Eligibility is re-checked against the locked row at completion time, so an Account suspended
  between request and completion cannot be revived by a secret issued while it was still active.

  `outbox.NoticeDelivery` was added rather than reusing `VerificationDelivery` with an empty token.
  The completion notice carries no actionable secret, but the destination is still PII, so it stays
  inside authenticated ciphertext under a type that cannot be misread as carrying a usable token.

  Four properties were mutation-checked: dropping epoch advancement, dropping the completion-time
  eligibility recheck, dropping the revocation, and replaying a consumed secret each failed their
  tests.

  **Corrected after review: the completion endpoint was a CPU-exhaustion surface.** Argon2id and
  compromised-password screening ran before the reset secret was validated, so an unauthenticated
  caller could post arbitrary tokens and force expensive hashing without holding a secret. A cheap,
  non-consuming preflight now rejects unknown, expired, consumed, superseded, and wrong-purpose
  secrets first. It takes no lock and is advisory only — the locked revalidation inside the
  transaction remains authoritative, so no race safety is traded away.

  The proof is an invocation count, not a stopwatch. An injected screener must be called **zero**
  times for each of the five refusal classes, and once for an accepted reset. `screenCompromised`
  runs immediately before `HashPassword` inside `prepareCredential`, so a zero count establishes the
  hash was never reached as a structural consequence rather than an inference from timing. Removing
  the preflight makes every refusal case report one call.

  Completion also gained its own rate policy instead of the generic admission one. The generic policy
  was actively unsuitable: its identifier dimension keys on the presented token, which an attacker
  varies freely, so that dimension contributed nothing against random-token flooding. The dedicated
  policy tightens network to 10/min, endpoint to 20/min, anonymous to 5/min, and global to 60/min.
  The anonymous dimension keys on `AnonymousID`, which is read from the signature-verified anonymous
  session cookie — server-issued, and derived from neither the token, its digest, nor any body field.

  `superseded_at` now comes from `clock_timestamp()`, the statement clock taken after the row lock,
  so it records when supersession actually happened. The earlier `GREATEST` clamp fixed the crash but
  recorded a fictional time; `GREATEST` is retained only as a clock-skew backstop between the
  application clock that writes `issued_at` and the database clock.

- [x] **4. Deliver bilingual recovery screens — 75 minutes.** Arabic/English request and
  reset-completion screens with generic outcome copy, no Account-existence signal, and no
  browser-persisted secret.
  **Stop condition:** RTL/LTR, phone/desktop, keyboard, expired-secret, and reused-secret paths pass
  frontend checks and manual inspection. **Met, after two defects found by browser testing.**

  `/recover` and `/recover/reset` ship in both languages, the completion route is now mounted, and
  sign-in links to recovery. The reset bearer travels in the URL fragment, which is never sent to the
  server, so it cannot reach access logs or a `Referer`.

  **Defect 1 — the fragment scrub was undone by hydration.** One `replaceState` in an effect loses a
  race with the App Router restoring its own URL snapshot, so the one-time token stayed in the
  address bar, and therefore in history and in anything the reader might screenshot or share. This
  affected the **already-shipped S1B1 verification flow** as well as the new recovery screen.
  Scrubbing now re-asserts on a bounded, self-terminating interval.

  **Defect 2 — a successful scrub made the form disappear.** React remounts components in
  development, which recreates component refs, so the second mount re-read the fragment the first had
  just emptied and fell into the missing-link state. Capture and scrubbing are now fully independent:
  capture is module-scoped, monotonic, and can never be walked back by a scrub that succeeded.

  Capture slots are **namespaced by purpose**. A single shared slot would let a verification token be
  read out of module memory by the recovery screen after a client-side navigation and submitted as a
  reset secret. The server would refuse it, but that is not a boundary to leave to the server. The
  app exposes no client-side route between those two screens today, so this is proven by unit test
  and mutation check rather than in the browser.

  The raw bearer is released from module memory on a terminal outcome only — success, or a definitive
  `TOKEN_INVALID`. It is deliberately **kept** after a network error, timeout, abort, rate limit,
  password-policy refusal, or 5xx, because the server may not have consumed the secret and the holder
  must be able to retry with the link they were sent.

  A third, smaller defect was fixed on the way: error messages were stored as resolved strings, so
  switching language left a stale-language error on screen. They are stored as keys and resolved at
  render.

  Browser evidence, on a **real document load** rather than a same-document fragment change:

  | Property | Result |
  |---|---|
  | URL after 2.5s | scrubbed, and stays scrubbed |
  | Reset form present | yes |
  | Bearer in DOM | no |
  | Browser storage | `gradex.locale` and `theme` only |
  | After locale switch | form present, URL clean, bearer absent, error re-resolves |

  Copy was corrected to state the real 15-character minimum from `validation.ts`; the first draft
  said 12.

- [x] **6. Prove the complete Student journey end to end — 75 minutes.** Run
  `register → verify → login → rotate → reject reuse → logout → recover → login` against real
  PostgreSQL, Redis, and MinIO, and expand the staged bootstrap-Admin denial proof across S1B's
  protected Identity surface.
  **Stop condition:** the full chain passes in one run with correct Identity evidence at each step,
  and the bootstrap Admin is denied everywhere the expanded proof reaches. **Met.**

  `TestCompleteStudentAuthenticationJourney` mounts the admission and session boundaries on one
  engine, in the order and with the shared anonymous keys `NewRouter` uses, and drives the whole
  chain through a single cookie jar against real PostgreSQL. The per-boundary tests each build half
  of this surface; the journey exists only where the halves meet, and what it proves is that the
  artifacts one step produces are the artifacts the next step accepts.

  Verification and reset links are followed without a mail transport by seeding the services with
  repeating fixed randomness, so the nth action secret is predictable.

  The evidence trail is asserted, not assumed: `STUDENT_REGISTRATION_ACCEPTED`,
  `STUDENT_EMAIL_VERIFIED`, `SESSION_CREATED`, `SESSION_RENEWED`, `SESSION_LOGGED_OUT`,
  `PASSWORD_RESET_REQUESTED`, and `PASSWORD_RESET_COMPLETED` must all appear for the journey Account.

  **The first version of this test was vacuous and was rewritten.** It recovered after logout, so no
  live family existed and "no live families after recovery" would have held whether or not recovery
  revoked anything. The journey now signs in again before recovering and performs the recovery from a
  second browser, as a locked-out person would. That leaves a live family for recovery to kill, and
  the still-open browser is checked to stop resolving afterwards — dead in fact, not merely marked
  dead in a row.

  Mutation-checked, with one informative negative result. Removing `revokeAllSessionFamilies` fails
  the journey. Removing **session-epoch advancement does not** — row revocation already kills the
  family in this scenario, so the epoch is redundant here. The epoch guards a family created
  concurrently with the reset, which the journey does not exercise; that property is covered by
  Must 3's `TestCompletePasswordResetIsAtomicAndInvalidatesEverySession`, which does fail when epoch
  advancement is removed. Both tests are needed, and neither subsumes the other.

  **On expanding the bootstrap-Admin denial proof: S1B added no capability-gated route.** Its new
  routes are anonymous (registration, verification, reset request and completion) or session
  lifecycle (resolve, renew, logout), and none takes a capability decision, so the protected-route
  table is unchanged. Recording that is the honest answer rather than padding the table.

  What S1B did add is a second way to replace the bootstrap Administrator's out-of-band password, so
  that path is now proven not to weaken the restriction it satisfies.
  `TestBootstrapAdminRecoveryRotatesWithoutGrantingAccess` runs the real `Bootstrap` command, confirms
  the Admin starts `ACTIVE`/`CHANGE_REQUIRED`, recovers, and asserts the credential returns to

  `CHANGE_REQUIRED` is correct because recovery achieves the rotation the restriction exists to force
  — and it is safe only because recovery grants no access of its own, which is what the family counts
  assert.
