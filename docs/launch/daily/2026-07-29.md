## Must

The bootstrap chain is ordered and each link depends on the one above it. It cannot be worked out of
sequence — see [SLICES.md §5.1](../SLICES.md#51-bootstrap-chain--fixed-order-s1a).

- [x] **1. Bootstrap schema and state.** Accounts with immutable role, password credentials, an
  explicit Identity-owned constrained `PASSWORD_CHANGE_REQUIRED` marker that does not overload
  `accounts.status`, and a dedicated bootstrap singleton/completion record that does not reuse
  shared `idempotency_records` as domain uniqueness.
  **Done at `90f92ec`** — migration `0002_identity_bootstrap` adds `accounts`,
  `password_credentials`, and `bootstrap_operations`. Both M1 obligations land as database
  guarantees: `CHANGE_REQUIRED` is a `credential_state` on the credential, leaving `accounts.status`
  free to read `ACTIVE` for the same Account; and the bootstrap singleton is a `BOOLEAN PRIMARY KEY`
  constrained to `TRUE`, so a second attempt fails on the key rather than on bypassable application
  logic. `accounts.role` is immutable by trigger, `normalized_email` is unique and must be lowercase,
  a password hash must be Argon2id-encoded, and a verified timestamp cannot coexist with
  `PENDING_VERIFICATION`. Every constraint was exercised against real PostgreSQL and refused what it
  claims to refuse. The migration integration test now uses `Down()` and checks both migrations;
  CI schema verification and `MaxSchemaVersion` move to 2.
- [x] **2. Controlled one-off bootstrap command.** Its own `cmd/` entrypoint, not an HTTP endpoint,
  ordinary worker, or schema migration.
  **Done at `d85d5a0`** — `cmd/bootstrap-admin` runs the §4.5 operation in one transaction:
  advisory lock, prove no completed bootstrap, prove no existing Admin, validate the password
  policy, create the verified `ACTIVE` Admin with a `CHANGE_REQUIRED` credential, write Audit, mark
  the operation complete. The initial password is read only through `config.SecretResolver`; there
  is no password flag and two tests fail if one is added. Migration `0003_audit_events` adds the
  append-only Audit table the transaction writes into — §17 requires the evidence row to commit
  with the change it evidences, so Audit had to exist before this link could.
  Verified end to end against real PostgreSQL: missing password refused, Administrator created,
  same-operation-ID retry read back the recorded result without creating anything, different
  operation ID failed closed, production gate refused both directions, `-password` rejected as
  undefined, and the plaintext appeared nowhere in a full `pg_dump`.
- [x] **3. Restricted bootstrap-session policies.** Deny-by-default typed authorization permitting
  only password change and session termination.
  **Done** — `identity.Authorize` is the single decision point over a closed `Capability` set, with
  explicit precedence: incoherent principal → suspension → `CHANGE_REQUIRED` → unverified → role.
  The restricted state overrides role, so the bootstrap Admin holds `ADMIN` and is still refused
  Admin, financial, security, retention, provider, and content-management capabilities. Authority is
  derived from Account and credential state on every request through `DBPrincipalResolver`; no
  capability column was added to `sessions`, and there is no session cache to invalidate — which is
  what makes a cleared requirement or a suspension take effect on the next request.
  `requireCapability` runs before every ownership and Entitlement check, and `NewRouter` refuses to
  build without a resolver so protected routes cannot ship with no decision at all.
  Typed deny reasons go to `authorization_denied` in the log; the client always gets the same
  `NOT_AUTHORIZED` body, per §5 and §6.1.
- [x] **4. Mandatory password-change completion — preparation half.** Normal recent-authentication
  rules and Argon2id.
  **Done** — migration `0004_sessions` adds `sessions` and immutable `session_credentials`
  (digests only, never credentials; one CURRENT generation per family by partial unique index;
  identity and supersession immutable by trigger). `PreparePasswordChange` locks Account → credential
  → session in a fixed order, rechecks status, epoch, generation, and recent authentication, verifies
  the current password for a voluntary change, and returns the new Argon2id hash **without mutating
  anything**. `RECENT_AUTH_WINDOW` config defaults to 15 minutes and is refused if it is not below
  `SESSION_IDLE_EXPIRY`, where it could never bind.
- [x] **5. Session rotation and restriction removal.** Atomic: neither half may land alone.
  **Done at `4ba1632`** — `CompletePasswordChange` owns one PostgreSQL transaction across Argon2id
  replacement, clearing `CHANGE_REQUIRED`, superseding generation N, minting and storing only the
  digests for generation N+1 and its CSRF token, re-establishing the current role-scoped session
  windows, revoking other families where required, advancing the Account revision, and appending
  matching Audit evidence. It returns browser credentials only after commit. The farthest injected
  failure, at Audit insertion, rolls every earlier effect back.

> **Links 4 and 5 are one feature boundary.** Link 4 ships no HTTP route — verified: nothing in
> `router.go` references a password. Nothing clears `CHANGE_REQUIRED`, rotates a session, or issues a
> cookie until link 5 can do all of it in one transaction. Every link-4 failure path leaves the old
> password, restriction state, and session authoritative, asserted by `assertNothingMutated` in the
> integration tests.

Today's result must not be recorded as the final proof. It demonstrates that the deny path works
through the real chain; it does not demonstrate coverage.

**S1A result — initial end-to-end denial evidence, recorded 2026-07-29.** The restricted bootstrap
Administrator is refused on all six protected routes that exist
(`upload-url`, `complete`, `retry`, `publish`, `playback-url`, `progress`), asserted through the real
router and middleware chain rather than against `Authorize` in isolation. Confirmed twice: in
`internal/httpapi/authorization_test.go`, and manually against the running API with a real
bootstrapped Admin over HTTP — four routes returned 403 with an identical `NOT_AUTHORIZED` body while
the log carried `PASSWORD_CHANGE_REQUIRED`.

The counter-evidence matters as much: clearing the requirement moved the same request from **403 to
404**, meaning it passed the policy and the ownership check and reached the handler. Re-setting
`CHANGE_REQUIRED` returned it to 403. So the deny path is not "deny everything". Suspension logged
`ACCOUNT_SUSPENDED` and an unknown identifier logged `PRINCIPAL_NOT_FOUND`, both with the same
uniform client response.
