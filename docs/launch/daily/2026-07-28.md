## Carried Obligations

Produced by Must 1. These are inputs to the slice register and to the July 29 Authentication/RBAC
slice, not optional follow-ups. Each exists because §4.5 requires state or an execution home that the
July 26 domain design does not enumerate — gaps in the table inventory, not contradictions in §4.5.

1. A constrained `PASSWORD_CHANGE_REQUIRED` marker. It is not an `accounts.status` value: §4.5
   creates the bootstrap Admin as `ACTIVE` *and* password-change-required. Neither `accounts` nor
   `password_credentials` carries it today.
2. A singleton bootstrap-operation marker with its own uniqueness constraint. `idempotency_records`
   cannot serve this role — domain §2.2 defines it as "not a substitute for domain uniqueness," and
   singleton-ness is precisely domain uniqueness.
3. Bootstrap capability restriction derived from obligation 1 rather than from new session state, and
   enforced deny-by-default by every §6.1 module policy. This is an authorization-surface
   requirement of July 29, not a schema one.
4. The bootstrap Administrator implemented as a controlled one-off release job in its own `cmd/`
   entrypoint. §4.5 forbids an HTTP endpoint or ordinary worker, and the architecture's container
   table offers no other home; the architecture's "controlled one-off release job" class (used for
   migrations) is the correct execution class. It is not itself a migration.
