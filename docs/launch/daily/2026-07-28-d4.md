## Progress

### M4 — complete

[`specs/005-media-and-entitlement-evaluation/`](../../../specs/005-media-and-entitlement-evaluation/spec.md)
is frozen: spec, plan, research, data model, the delivery contract, 32 tasks, and the quickstart.
**No S4 implementation exists**, which was the acceptance condition.

The plan spends its structure on the two boundaries that make S4 Tier 3, and leaves the pipeline
conventional.

**1. S4 evaluates Entitlements and must never create one.** Guarded four ways rather than by
convention, because conventions failed in S1C and S2 in exactly this shape:

- `internal/entitlement` exports no creation surface — not discouraged, unavailable.
- The seed mechanism sits behind `//go:build !production`, **absent from the production binary**
  rather than disabled within it. A config flag that *could* be flipped in production is not
  exclusion, and this project already holds `AUTH_FAKE_MODE` to that standard.
- A test builds with production constraints and asserts the seed symbol is unreachable — that is the
  defence that survives the next contributor.
- **`source_order_item_id NOT NULL` in the schema**, from this migration, though S7 has not built the
  producer yet. It makes an Entitlement without an Order **unrepresentable**, so neither the seed nor a
  future support script can cheat.

**2. Nothing unscanned is ever reachable.** `LG-014` is unresolved and may stay that way, so the design
question was *what does an unresolved gate degrade?* — and the answer is availability, never safety.
Deliverability is `state == READY`, expressed once. Not an exclusion list: an exclusion list is a place
to forget a state, and a reviewer cannot tell a forgotten exclusion from a deliberate one. There is no
scan outcome meaning "not scanned but proceed", and scanner **absence** leaves assets in `SCANNING`,
which is already non-deliverable.

Two smaller decisions worth naming:

- **The scan result binds to an exact stored object version, not to the logical asset.** A logical
  binding would let a re-upload inherit a previous pass — silent, and the asset is unscanned.
- **Signed access does not promise what it cannot deliver.** An issued presigned URL cannot be revoked;
  the exposure window is bounded by signature lifetime, and the plan says that instead of claiming
  instant revocation. Same class of correction as S3's OD-002.

The slice keeps the calendar's own D7/D8 split — pipeline, then delivery and evaluation — with three
mandatory gates: fail-closed proven **per scanner failure mode individually**, no-creation-path proven
against a production build before any delivery work starts, and denial uniformity across all eight
causes. Ten required mutations are enumerated rather than left to the builder's judgement.

#### Round one — HIGH: a handler that reported success and did nothing

`submitCourse` was mounted in production with this entire body:

    c.JSON(http.StatusOK, gin.H{"status": "submitted"})

An owning Instructor received `200 {"status":"submitted"}`. No completeness validation, no taxonomy
validation, no `DRAFT → PENDING_REVIEW` transition, no read-only lock, no audit row, no outbox intent.

**It is the first instance of this class to fail open.** Every previous one failed closed — unwired
`WithStaffFoundation` returned 401, S1C's unset context key returned 401, S2's tautological sweep
silently passed. This one actively told the caller the work was done.

Nothing could catch it: the route correctly carried `RequireCourseOwnership`, so the authorization
sweep passed, and every gate was green. It was found by reading the handler body.

Removed rather than stubbed to `501`. **An absent route returns 404 and tells the truth.** Submission
is Phase 4 and mounts the route when it does something.

#### Round two — CRITICAL: the entire surface was unreachable in the running API

`WithCatalogFoundation` was never called by `cmd/api`. `routerConfig.catalog` was nil,
`mountCatalogRoutes` never ran, and **all sixteen routes returned 404 in the production binary.**
User Story 1 did not exist in the product.

**This is S1C's first critical verbatim** — *"`WithStaffFoundation` was never wired into `cmd/api`"* —
and the dispatch brief had named that precedent explicitly and said to assume it was the most likely
failure mode.

Every test passed because the tests construct `NewRouter` **with** the catalog foundation, which the
production binary never built. That is not a bug in the tests; it is the gap in what the derived
ownership sweep can prove. It establishes *every mounted owned route carries ownership* and says
nothing about *the production binary mounts the routes at all*.

Fixed two ways: `cmd/api` now builds every foundation through one shared
`buildProductionFoundations`, and `TestProductionRouterWiringHasNoMissingSurfaces` drives **that same
builder**, so the test cannot diverge from what `main()` constructs.

**Known limitation, recorded rather than implied.** That test's expected-surface list is
**hand-maintained**. A fifth foundation added without a row would still ship unmounted. It closes this
defect, not the class — and the builder's own report answered "what this does not prove" by
discussing reverse proxies and DNS rather than naming this, so it is named here instead.

#### The rejection: a run that produced no report, and a suite that did not pass

The first dispatch **ended mid-tool-output** with no structured report — no task account, no route
table, no mutation results. That is the implementation equivalent of a review returning no verdict,
and it was treated as an incomplete dispatch rather than as complete-with-findings. All six required
mutations were unverified.

It also did not pass. The phase's own headline test failed:

    --- FAIL: TestSubmissionValidationReportsAllDefectsInOneResponse
        expected 422 for incomplete submission, got 500

**Root cause: nested open cursors.** The revision-graph loader opened a cursor over sections, then
issued a query per section while it was still open, then a third per lesson. pgx cannot query a
connection with open `Rows` — against a pool it sometimes borrows another connection and appears to
work, inside a transaction it always fails with `conn busy`.

**The pattern was pre-existing**, shipped in Phase 3 at `ae638c0`; `git diff` confirmed this dispatch
did not introduce it. Nothing had exercised it hard enough to fail. Phase 4 is what surfaced it — the
same shape as S1B3 surfacing two S1B1 defects, and an argument for exercising committed code rather
than trusting that it passed once.

Fixed by draining and closing the outer cursor, then batching lessons and files with `= ANY`. Three
queries instead of 1+N+N·M, identical behaviour inside and outside a transaction. **Pool widening and
a `conn busy` retry were both refused in the brief** — either would have hidden it and returned it
under load.

A debug `fmt.Printf` writing raw error internals to stdout was also removed. It bypassed the
`logging` package's closed field allowlist — the control built specifically so error detail cannot
reach telemetry unreviewed.
