## Decisions

- The provisional production architecture will optimize for the lowest operational burden. Managed
  infrastructure is preferred even when it costs moderately more, but provider-specific behavior
  must remain behind configurable boundaries.
- This is an architecture-direction decision, not approval of a provider, budget, or production
  operating envelope. `LG-019` remains open.
- No hard data-residency boundary is assumed before counsel resolves `LG-004`. The provisional
  design will prefer a suitable managed Middle East region, require encryption in transit and at
  rest, document cross-border data handling, and preserve a credible migration path.
- The approved topology direction is split managed PaaS: an edge-hosted frontend, separately
  scalable managed API and worker processes, managed PostgreSQL and Redis, and managed object
  storage/CDN. This balances low operational burden with replaceable provider boundaries.
- Unified managed PaaS was not selected because it increases platform coupling. Cloud-managed
  primitives were not selected because their networking, identity, and operations burden is too
  high for the solo-operated August 15 launch.
- Architecture Section 1 is approved: modular-monolith drivers, managed operations, single-region
  launch, existing stack preservation, independently scalable API/worker processes, replaceable
  external adapters, PRD performance/availability targets, and the provisional load/recovery
  envelope.
- Source media uses versioned durable object storage. Successfully completed uploads should not be
  lost under normal provider failure scenarios. The secondary backup-copy target is RPO no greater
  than 24 hours, with recovery RTO no greater than 8 hours.
- Section 1 values remain provisional rather than resolving `LG-019`: 5,000 registered accounts,
  500 concurrent sessions, 100 concurrent playback starts, 100 API requests/second in short bursts,
  20 concurrent uploads, two transcodes per worker, PostgreSQL RPO no greater than 15 minutes/RTO
  no greater than 4 hours, and deployment rollback within 30 minutes.
- Architecture Section 2 is approved: system actors and external services; separate frontend, API,
  worker, PostgreSQL, Redis, and object-storage/CDN containers; modular-monolith ownership; explicit
  application contracts; transactional coordination where atomicity is required; transactional
  outbox delivery; and provider SDKs restricted to outer adapters.
- Catalog owns only course-facing review state and feedback. Moderation reports and enforcement are
  Admin workflows, with privileged actions recorded through Audit.
- Architecture Section 3 is approved: edge frontend; HTTPS API; private worker/data boundaries;
  direct signed media transfer; independently scalable API and worker processes; isolated queues;
  immutable deployables; isolated staging/production environments; controlled migrations and
  rollbacks; managed backups, secrets, and observability; and environment-driven provider
  portability.
- The stateless API supports horizontal scaling and health-checked deployment. It may run one
  instance at low launch load and scale to at least two when availability, traffic, or deployment
  requirements justify it; two always-on instances are not required before `LG-019`.
- Staging remains isolated from production but may use smaller resource sizes or scale to zero when
  inactive.
- Architecture Section 4 is approved: PostgreSQL transaction/outbox processing, payment and
  Entitlement atomicity, verified webhook reconciliation, quarantine-first media processing,
  Redis/job reconstruction, fail-closed provider behavior, and the ordered recovery procedure.
- Idempotency keys are mandatory for sensitive commands and externally retried writes, including
  order creation, payment actions, refunds, upload completion, retries, and equivalent operations.
  They are not required for every API request.
- Architecture Section 5 and the complete design are approved: security and trust boundaries,
  observability, validation, open provider/gate decisions, and production acceptance.
- The formal result is
  [Gradex Platform Architecture](../../superpowers/specs/2026-07-25-platform-architecture-design.md).
- Production approval requires no unresolved critical defects. A high-severity defect requires
  documented risk acceptance, mitigation, and owner approval; this does not waive a required launch
  gate.
