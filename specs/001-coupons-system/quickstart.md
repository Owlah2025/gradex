# Quickstart / Validation Guide: Coupons System

> Status: Proposed post-implementation validation guide; Coupon and its platform prerequisites are
> not implemented in the current repository.

Run-guide to prove the feature works end-to-end. Implementation details live in `tasks.md`
(generated by `/speckit-tasks`) and the code; this is the validation checklist.

## Prerequisites

- Platform system design and feature tasks have finalized the proposed API/error contracts.
- Real Account/Admin/Student authorization, Course/Section prices, Orders/payments,
  Enrollment/Entitlement, Refunds, and audit facilities are implemented.
- The final Coupon migration is applied using `make migrate-up` from `backend/` against an explicit
  non-production test database.
- Test fixtures create real test Accounts and Orders. Current `backend/scripts/seed.sql` only seeds
  video-slice Course/Section/Lesson IDs and fake per-Lesson entitlements; it is not an
  auth/Coupon/commerce seed.

The paths/status codes below are proposed. Update this guide if platform system design changes them.

## Scenario 1 — Admin creates a percentage coupon

1. `POST /api/v1/admin/coupons` with `WELCOME20`, `percentage`, `20`, and global cap `100`.
2. Expect `201`; admin detail shows `reserved_count: 0`, `consumed_count: 0`.
3. Re-POST the same code → expect `409 duplicate_code`.

## Scenario 2 — Student previews (no side effects)

1. `POST /api/v1/checkout/coupons/preview` for a Course priced at 40 KWD using code `WELCOME20`
   and test Course ID `00000000-0000-0000-0000-000000000040`.
2. Expect `valid:true`, `subtotal_amount:40000`, `discount_amount:8000`, `total_amount:32000`,
   `free:false`.
3. `GET /api/v1/admin/coupons/00000000-0000-0000-0000-000000000020` →
   both counts remain `0` (preview committed nothing).

## Scenario 3 — Paid reservation then consumption (needs orders/fake)

1. Create an Order with the code. Expect one `RESERVED` row and `reserved_count = 1`.
2. Simulate the gateway success webhook (idempotency key `K`).
3. Expect Enrollment/Entitlement; row `CONSUMED`; `reserved_count = 0`, `consumed_count = 1`.
4. Replay webhook → counts/rows unchanged (BR-033/129).

## Scenario 4 — Free (100%) coupon grants directly, no gateway

1. Admin creates `FREEBETA` = `percentage 100` (or `fixed ≥ price`).
2. Student creates an order → `total_amount = 0` → free-grant path.
3. Expect: Enrollment/Entitlement granted with the Order's disclosed Course-configured expiry;
   one redemption row;
   `consumed_count = 1`; **no gateway session created**.

## Scenario 5 — One consuming Redemption per Student (exact)

1. Same student attempts the same coupon again for a new eligible item.
2. Expect rejection `already_used` while the first Redemption remains consuming.

## Scenario 6 — Frozen fields after redemption

1. `PATCH /api/v1/admin/coupons/00000000-0000-0000-0000-000000000020` changing
   `discount_value` after Scenario 3.
2. Expect `409 frozen_field`. Changing `is_active`/`valid_until`/`max_redemptions`/`targets`
   still `200`.

## Scenario 7 — Delete guard

1. Delete a redeemed Coupon → expect `409 has_redemptions`.
2. Delete an unredeemed Coupon → expect `204`.

## Scenario 8 — Exact global capacity under race

1. Coupon cap `= 1`; two Students concurrently create paid Orders.
2. Exactly one reserves/creates. The other receives `cap_reached`; total reserved + consumed is `1`.
3. Expire/cancel the reserved Order and verify capacity is released for a later Order.

## Scenario 9 — Refund eligibility release

1. Partially refund the paid Coupon Order; a new use by the same Student remains `already_used`.
2. Confirm additional Refund(s) until cumulative confirmed refunds equal the captured amount.
3. Expect the original Redemption to remain in history with released state and
   `consumed_count` unchanged.
4. The Student may use it again only if global capacity remains (or the cap is increased).
5. Replay the full-refund confirmation; it does not create a second release or alter counts again.

## Unit-test checklist (no DB)

- discount math: percentage rounding, fixed clamp-to-zero, negative guard, `> subtotal` guard.
- validation predicates: window (before/after/open-ended), scope (platform/targeted match &
  miss), active, cap boundary, and consuming-eligibility boundary.
- code normalization: lowercase/whitespace input matches stored uppercase code.

## Done when

Every scenario passes and no monetary value is a float anywhere in the feature.
