# Quickstart / Validation Guide: Coupons System

Run-guide to prove the feature works end-to-end. Implementation details live in `tasks.md`
(generated by `/speckit-tasks`) and the code; this is the validation checklist.

## Prerequisites

- Backend running against a Postgres with migrations applied through `0002_coupons`
  (`make migrate` or the repo's migration command).
- An admin user and a student user seeded (see `backend/scripts/seed.sql`).
- Until the orders subsystem exists, the integration tests use the minimal fake `orders`
  fixture described in [contracts/order-integration.md](contracts/order-integration.md).

## Scenario 1 — Admin creates a percentage coupon

1. `POST /api/v1/admin/coupons` with `WELCOME20`, `percentage`, `20`, cap `100`, per-user `1`.
2. Expect `201`; `GET /api/v1/admin/coupons` shows it with `redemption_count: 0`.
3. Re-POST the same code → expect `409 duplicate_code`.

## Scenario 2 — Student previews (no side effects)

1. `POST /api/v1/checkout/coupons/preview` `{code:"WELCOME20", item_type:"course", item_id:<40 KWD course>}`.
2. Expect `valid:true`, `subtotal_amount:40000`, `discount_amount:8000`, `total_amount:32000`,
   `free:false`.
3. `GET /admin/coupons/<id>` → `redemption_count` still `0` (preview committed nothing).

## Scenario 3 — Paid redemption commits on grant (needs orders/fake)

1. Create an order with the code (order creation snapshots discount/total).
2. Simulate the gateway success webhook (idempotency key `K`).
3. Expect: enrollment granted; one `coupon_redemptions` row; `redemption_count = 1`.
4. **Replay** the same webhook (key `K`) → still one redemption row, `redemption_count = 1`
   (no double-count — BR-033/129).

## Scenario 4 — Free (100%) coupon grants directly, no gateway

1. Admin creates `FREEBETA` = `percentage 100` (or `fixed ≥ price`).
2. Student creates an order → `total_amount = 0` → free-grant path.
3. Expect: enrollment granted with 150-day term from grant time; one redemption row;
   `redemption_count = 1`; **no gateway session created**.

## Scenario 5 — Per-user limit (exact)

1. Same student attempts the same coupon again for a new eligible item.
2. Expect rejection `already_used` (unique `(coupon,user)` + BR-024).

## Scenario 6 — Frozen fields after redemption

1. `PATCH /admin/coupons/<id>` changing `discount_value` after Scenario 3.
2. Expect `409 frozen_field`. Changing `is_active`/`valid_until`/`max_redemptions`/`targets`
   still `200`.

## Scenario 7 — Delete guard

1. `DELETE /admin/coupons/<redeemed id>` → `409 has_redemptions`.
2. `DELETE /admin/coupons/<unredeemed id>` → `204`.

## Scenario 8 — Soft global cap under race (integration test)

1. Coupon cap `= 1`. Two orders created (both pass creation-time validation).
2. Both grant transactions commit. Expect: both enrollments honored; `redemption_count = 2`
   (> cap) — documented soft-cap behavior (BR-129), not a bug.

## Unit-test checklist (no DB)

- discount math: percentage rounding, fixed clamp-to-zero, negative guard, `> subtotal` guard.
- validation predicates: window (before/after/open-ended), scope (platform/targeted match &
  miss), active, cap boundary, per-user boundary.
- code normalization: lowercase/whitespace input matches stored uppercase code.

## Done when

Every scenario passes and no monetary value is a float anywhere in the feature.
